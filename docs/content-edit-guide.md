# QuestDP Content Edit Guide

이 문서는 개념·문제 수정 전에 먼저 읽는 짧은 기준서다. 상세 작업 이력은 `docs/content-edit-log.md`에서 필요한 키워드로 찾아본다.

## 1. 수정의 기준

- 기준 사용자는 ADsP·SQLD를 처음 보는 모바일 학습자다.
- "시험 요약"보다 "처음 봐도 이해되는 흐름"을 우선한다.
- 한 화면에는 한 개념만 선명하게 둔다.
- 긴 정의문은 상황 예시, 비교, 짧은 말투로 풀어쓴다.
- PDF, 교재, 타사 문제 문장은 그대로 옮기지 않는다.
- 사용자가 직접 고친 표현은 이후 콘텐츠 수정의 기준 데이터로 삼는다.

## 2. 개념 설명 원칙

- 한 스텝에 서로 다른 개념이 섞이면 분리한다.
- 낯선 용어는 처음 등장할 때 짧게 설명하거나 클릭 설명으로 연결한다.
- 축약어만 던지지 않는다. 먼저 전체 명칭을 보여준다.
- 암기어는 실제 개념이 아니라 기억 도구로만 설명한다.
- 설명은 "무엇이다"에서 끝내지 말고, 왜 필요한지와 쉬운 예시를 붙인다.
- 모바일에서 한눈에 읽히도록 문장을 짧게 나눈다.

## 3. 문제 작성 원칙

- 개념을 배운 직후 바로 확인 문제를 붙인다.
- 문제는 방금 배운 개념을 실제 예시에서 고르게 만든다.
- 정답 위치가 반복되지 않게 섞는다.
- 오답 선택지는 너무 터무니없게 만들지 않는다.
- 해설은 정답을 다시 말하는 것이 아니라, 왜 맞고 왜 헷갈리는지 설명한다.
- SQL 문제는 SQL 표준, Oracle, MySQL 등 기준을 필요한 경우 명시한다.

## 4. UX 원칙

- 모바일 우선으로 본다.
- 카드가 너무 작거나 글이 빽빽하면 개념을 나누거나 시각 자료를 추가한다.
- 그림은 장식이 아니라 개념 이해를 도와야 한다.
- 새로 나오는 개념 카드나 보조 설명은 갑자기 튀어나오지 않게 자연스러운 모션을 둔다.
- 문제 풀이에 필요한 텍스트는 줄이지 않는다. 주변 안내 문구만 줄인다.

## 5. 서버 연동 원칙

- QuestDP v2 문제풀이에서는 Supabase `public.questions`가 문제 예약, 채점, XP 지급의 기준이다.
- 로컬 JSON에 문제가 있어도 Supabase에 같은 `id`가 없으면 실제 플레이에서 실패한다.
- `quizId`나 `extraQuizIds`를 추가하면 로컬 수정만으로 완료가 아니다.
- 서버 반영 전에는 "수정 완료"라고 말하지 않는다.
- 서버에 없는 문제를 클라이언트 fallback으로 풀게 만들지 않는다.

## 6. 기록 원칙

- 중요한 콘텐츠 수정은 `docs/content-edit-log.md`에 짧게 남긴다.
- 기록에는 다음을 포함한다.
  - 사용자가 발견한 문제
  - 수정한 방향
  - 사용자에게 주는 좋은 영향
- 반영 파일과 Supabase 반영 여부
- 같은 실수를 막는 규칙은 이 guide 또는 checklist로 승격한다.
